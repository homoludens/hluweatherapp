## Context

See `proposal.md` for motivation. `WeatherProvider` and `CachingWeatherRepository` currently route two sources, keyed by provider and location. `HourlyTableColumn` already includes precipitation probability and the other configurable variables; MET Norway maps the probability to `null` because `KtorMetNoApi` requests `compact`, not `complete`. Forecasts feed foreground screens, notifications, and both widgets; the route forecast uses a separate Open-Meteo source and is not controlled by the weather-provider setting.

Bright Sky serves `/weather` as hourly, station-based forecast/observation data and `/current_weather` as recent SYNOP observations. The documented `max_dist` default is 50 km, but the API accepts up to 500 km; the app's planned 50 km ceiling is a coverage policy, not an API limit. Forecast stations are sparser outside Germany. Visual Crossing supplies a Timeline response with `currentConditions`, daily records, and nested hourly records. The live anonymous endpoint returned HTTP 400 unless the request advertised gzip, then returned HTTP 200; a small anonymous request with `aqieur`, `pm2p5`, and `pm10` succeeded, while one including `et0` returned HTTP 401 for the entire request. These probes were made on 2026-11-08 for Berlin; they are observations, not a guarantee of coverage or future pricing.

## Goals / Non-Goals

**Goals:**
- Preserve a single provider-aware forecast pipeline and audit every existing weather setting against all four sources.
- Preserve interval, index-scale, unit, timezone, data-source, and missing-value semantics rather than forcing superficially similar values into the same meaning.
- Ensure optional or license-restricted fields cannot make an otherwise usable forecast fail.

**Non-Goals:**
- Bright Sky radar, new radar providers, map/radar rendering changes, or changes to the existing radar selection.
- Visual Crossing map tiles, historical datasets, provider-specific alert products, unrelated new weather columns, or replacing the route-specific Open-Meteo source.
- Bundling a shared Visual Crossing API key, adding an account/key-management screen, or relying on paid-only fields.

## Decisions

### Provider adapters, routing, and credentials

Add explicit `VISUAL_CROSSING` and `BRIGHT_SKY` identifiers, `WeatherSource` implementations, and Ktor adapters in the existing application dependency graph. Persist names as for current providers; register both in the source map and preserve the provider/location cache identity, stale fallback, cancellation, and notification/widget paths. Selection is independent of radar. Never label another forecast provider's response as the selected one. Alternative: separate UI-specific clients; rejected because they would bypass existing cache identity, refresh behavior, and background consumers.

Use Visual Crossing's [anonymous Timeline API](https://www.visualcrossing.com/resources/documentation/weather-api/free-weather-api-no-key/) in JSON and metric units, `include=days,hours,current`, limited to the forecast horizon and fields needed by the app. Advertise and decode gzip for anonymous requests; use the supported Ktor/OkHttp compression mechanism and test it explicitly. Respect `429`/`Retry-After`, bounded concurrency, cache freshness, and fair use; do not retry permanent authorization/field errors in a tight loop. The general Timeline documentation still contains a legacy `key (required)` line, but its anonymous guide and the successful gzip probe describe working keyless requests. Do not expose tokens, coordinates, or full request URLs in error messages or logs.

Use Bright Sky `/weather` for forecast records and `/current_weather` for a recent observation when available; request DWD units (°C, km/h, mm) explicitly, coordinate-based search, and enforce a 50 km station-distance ceiling as app policy (the API's `max_dist` defaults to 50 km but permits up to 500 km), respecting source metadata. If current observations are unavailable, use the nearest appropriately timed Bright Sky hourly forecast as a forecast-derived current value, not an invented observation. If no suitable station/record exists, use matching stale cache or report unavailability. Preserve timestamps and any needed source identity/distance; never use a far-away station silently. Request only the app's normal forecast window; derive daily summaries from the available hourly records in the location zone, without claiming incomplete days are complete or fabricating missing values. Handle missing sun times as unavailable and use the existing moon-phase calculation where needed.

It covers every `HourlyTableColumn` and every field in `CurrentWeather`, `DayForecast`, and the forecast-level timezone/moon-phase fields. `—` means the documented product has no semantically compatible field; `restricted` means the field is documented but access/coverage is conditional. A supported field is still nullable: upstreams omit values for some records, locations, or forecast horizons. Keep zero distinct from missing and validate ranges/finiteness.

For Visual Crossing, request optional air-quality elements separately from core weather when needed to isolate unavailable/restricted products; merge only matching instants and retain the source/scale. The upstream docs describe AQI as hourly/daily with limited history and forecast, not as a current AQI guarantee. Never request known restricted `et0` on the anonymous path. Add an explicit AQI representation/scale to the normalized/cache model so `aqieur = 3` can be displayed accessibly as category `3/6` (or equivalent named category), never as numeric Open-Meteo AQI 3. Offline mapping fixtures are under `app/src/test/resources/provider-fixtures/`; they are small, deterministic examples of documented shapes and units, not live responses. They include separated optional air-quality responses, MET Norway one- and six-hour periods, and Bright Sky source/interval metadata so tests do not depend on network access.

### Time and probability interval handling

Use absolute instants for records and an IANA timezone for each location. Visual Crossing already returns a zone; Bright Sky requires callers to supply a zone and MET Norway does not resolve one. Open-Meteo's docs caution that named-zone ISO timestamps may ignore DST changes in the requested range, so request Unix timestamps and convert with the returned zone for unambiguous instants. Resolve coordinates with an offline Android-compatible timezone-boundary lookup, cached per coordinates; evaluate Android support, data currency, app size, and MIT/ODbL notices before selecting/pinning the library (for example, [TimeZoneMap](https://github.com/dustin-johnson/timezonemap)). Do the lookup off the UI thread and preserve its result with the forecast. Never assume the device zone is the location zone. For an unresolvable/invalid zone, use a clearly identified UTC presentation rather than silently claiming local time; do not fabricate local-day extrema. Alternative: querying a third party for timezone on every refresh; rejected to avoid extra location disclosure, network dependency, and usage cost.

The pinned raw-boundary lookup retains unknown zone IDs and detects overlaps before validating the sole match against Android's timezone database; unknown, unavailable, or ambiguous matches use explicitly labeled UTC. It scans the compressed boundary archive on an IO dispatcher for each exact-coordinate cache miss to avoid retaining an approximately 50 MiB in-memory geometry index. On `small_phone`, a first lookup measured about 14–16 seconds, while repeated exact-coordinate lookups use the bounded in-process cache. This latency/memory tradeoff is accepted; do not quantize coordinates or choose an arbitrary overlap. A disk-backed spatial index is a possible future optimization, not part of this change.

Use Timeshape 2026b.29's unmodified 2026b boundary archive (approximately 23 MB compressed; MIT code, ODbL OpenStreetMap-derived data), with its documented Android zstd runtime. Read the archive's raw protobuf IDs and polygon geometry directly rather than Timeshape's index, which drops IDs missing from the device tzdb. Collect all intersecting raw IDs, deduplicate identical IDs, and resolve only a single device-supported ID. No match, multiple distinct IDs, or an unsupported ID means explicitly labeled UTC and no derived local-day summaries; archive failures are errors, not disguised as unknown locations. Scan off the UI thread and keep a bounded exact-coordinate cache; uncached lookups trade latency for avoiding a persistent in-memory global polygon index. Repeated civil hours retain distinct instants and display their offsets.

Use the existing preceding-hour convention for comparable hourly probability cells. Open-Meteo and Bright Sky probabilities explicitly describe the preceding hour. A MET Norway `next_1_hours` probability at instant `t` belongs to the hour ending at `t + 1h`, and is associated with that hour's row only when the corresponding instant exists. Never spread `next_6_hours` or `next_12_hours` probability over hourly cells, infer probabilities from precipitation amount, or turn missing into 0%. Keep period distinctions for precipitation totals, never sum overlapping intervals, and use instants through DST gaps/repeated hours. Add boundary, sparse-series, zero, long-range, and cache round-trip tests.

### Attribution, background work, and compatibility

Show Visual Crossing's required visible, nearby source attribution in each weather presentation, including small/medium widgets and forecast notifications; link in app views where practical, and use readable text where the host does not support links. Show Bright Sky and DWD credits per their applicable terms, and update the app credits documentation. Place widget credit without displacing the location-first header, refresh action, or accessibility, and test minimum supported sizes/font scales. Use the cached forecast's actual provider for attribution during stale fallback and protect asynchronous selection changes from cross-provider relabeling. A credits-only page is insufficient for Visual Crossing.

Extend cache DTOs with optional/defaulted additions; old entries must decode, and new provider/scale entries must round-trip without polluting another provider's cache. Downgrades may ignore new enum values and safely fall back to existing defaults. Keep widget/notification refresh scheduling and existing selected-location behavior unchanged. Alternatives: hard-code a new provider default or clear all cached forecasts; rejected to preserve installed users' settings and offline behavior.

## Risks / Trade-offs

- [Regional, sparse Bright Sky station coverage] → Enforce the app's 50 km distance policy (the API allows a wider query), report unavailability honestly, and test within and outside coverage; never silently switch providers.
- [Visual Crossing anonymous limits, gzip requirement, and evolving licensing] → Limit requests, isolate optional products, handle 401/403/429 and Retry-After, and document the probe date; no assumed fixed allowance.
- [Time-zone border data, size, and updates] → Pin and credit a compatible offline dataset, test DST and representative locations, perform lookup off the UI thread, and use a visibly identified UTC fallback when unresolved.
- [Variable definitions differ] → Keep category/index and reference/actual ET distinct, align probability periods by instant, and record a verified source-field matrix instead of mapping unlike values.
- [Widget attribution competes for space] → Test minimum sizes and accessibility; retain existing weather and interaction priorities while making provider credit visible.
- [Rapid provider changes and stale completions] → Keep provider/location identity through cache, results, and presentation; use delayed-response tests to prevent old data or credits replacing the current selection.

## Migration Plan

Add new enum entries without changing old serialized names, retain defaults, and make cache additions backward compatible. Deploy adapters and attribution with tests before enabling the new choices. On rollback, existing providers continue using their previous identifiers; an unknown new selection follows the existing invalid-provider fallback and new cache entries are ignored, without deleting saved locations or other preferences. Re-enable a new provider only after its requests and attribution satisfy current terms.
