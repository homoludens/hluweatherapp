### Follow-up investigation — public source volatility

- Inspected the installed MapLibre Compose 0.16.0 public sources. Native `MutableSourceHandle.isVolatile` sets a **source-wide** storage policy for subsequent tile requests; it does not clear previously cached tiles or reload in-memory tiles. `TileSetOptions` and the public `RasterTileSource` constructors have no volatility option. `MapResourceLoadRequest.storagePolicy` reports the policy but is not a response setting, and `MapResourceLoad.Bytes` provides no per-response `no-store` flag. The public ambient-cache controls apply to the entire runtime, not individual radar responses.
- Passed `publicSourceVolatilitySetterBeforeLayerPreventsRadarDiskWrites` on the installed native snapshot renderer with the existing 32 MiB runtime options. A raster source was present in the base style **without a radar layer**, then its public mutable handle was set volatile before the layer was introduced. The test observed no early radar requests, `Volatile` on every radar callback, and red radar pixels over a blue basemap. After closing the runtime, SQLite contained cacheable basemap tile rows and **zero** radar tile rows. The radar transport supplied controlled payloads marked non-cacheable, not real provider HTTP responses; the existing focused Ktor unit test separately checks parsing `Cache-Control: no-store`. This proves the mechanism in that snapshot setup, not safe installation for dynamically changing app sources.
- The documented [raster style-JSON `volatile` field](https://maplibre.org/maplibre-style-spec/sources/#volatile_1) is **not effective in the tested installed runtime**: `volatileStyleJsonIsIgnoredByInstalledNativeRuntime` observed `isVolatile == false`, eight `Permanent` callbacks across two fresh runtimes, 4 cacheable basemap rows and 4 radar rows. The second runtime reused its basemap cache but refetched the expired radar response. This retained test is a negative control describing the pinned runtime, not a solution.
- `compositionOwnedRasterSourceHasNoMutableVolatilityHandle` passed: a source declared by `RasterLayer` had `asMutable == null`, generated `Permanent` callbacks, and wrote radar rows. In the live-map `liveMapCompositionCannotSeeSourceAddedAfterStyleContentWasCreated` test, an imperatively added source could be marked volatile but a later `getBaseSource` lookup could not see it. A separate exploratory variant that directly declared the same imperatively owned source failed with `StyleHandleException: Source ID 'dynamic-radar' is owned by an imperative addition`; that crash-producing branch was removed after observation. These tests do not establish a supported dynamic two-slot attachment strategy.
- Latest full native class run: same command and environment as above, **6 tests, 1 failure, 0 errors, 0 skipped**. The four volatility/ownership experiments and the original hook/coverage proof passed; `noStoreResponsesAreNotPersistedByNativeCache` still failed with 4 radar rows instead of zero. The positive setter experiment is not integrated into the production renderer or bridge. A safe solution must establish volatility before *every* first request, including after source replacement and style reload, and address any previously cached/in-memory tiles without disabling or clearing the whole basemap cache.
- At that checkpoint the proposed direction for coordinator/user decision was to make every radar source volatile while retaining the 32 MiB native cache for basemap and the bounded app byte cache for cacheable radar. This forgoes native persistence for **cacheable** radar responses and requires a compatible dynamic-source/layer ownership strategy, neither of which was proven in the app. At that time the design anticipated native cached radar responses; a material design/verification update and approval were needed before integration. ### Approved volatile-only design — task 3.2 verification

- The user approved making all radar sources volatile.
