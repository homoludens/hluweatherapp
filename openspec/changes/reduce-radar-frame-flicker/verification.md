### Two-opacity ordering

The existing `MapLibreRadarBackend.promote()` calls `setLayerProperty` for the replacement and then the predecessor inside one `withPlatformMap` callback. The source-level chain for a **changed** opacity is:

1. FFI [`map_set_layer_property`](https://github.com/maplibre/maplibre-native-ffi/blob/c29b61a0c45a0471d1b1d2c0bce23a458b6a6440/src/map/map.cpp#L6829-L6871) calls `Layer::setProperty`; native [`RasterLayer::setPropertyInternal` and `setRasterOpacity`](https://github.com/maplibre/maplibre-native/blob/d695deef12fc64ee075a892c2d913c45fe8c7b42/src/mln/style/layers/raster_layer.cpp) replace the layer implementation and notify `onLayerChanged` for a changed value.
2. [`Style::Impl::onLayerChanged`](https://github.com/maplibre/maplibre-native/blob/d695deef12fc64ee075a892c2d913c45fe8c7b42/src/mln/style/style_impl.cpp) updates the layer list and calls `onUpdate`; [`Map::Impl::onUpdate`](https://github.com/maplibre/maplibre-native/blob/d695deef12fc64ee075a892c2d913c45fe8c7b42/src/mln/map/map_impl.cpp) constructs update parameters containing the current layers and passes them to the frontend in continuous mode.
3. FFI [`HeadlessFrontend::update` and `latest_update`](https://github.com/maplibre/maplibre-native-ffi/blob/c29b61a0c45a0471d1b1d2c0bce23a458b6a6440/src/map/map.cpp#L1968-L1995) publish/read that latest update under a mutex. The separate render thread's [`render_session_render_update`](https://github.com/maplibre/maplibre-native-ffi/blob/c29b61a0c45a0471d1b1d2c0bce23a458b6a6440/src/render/render_session_common.cpp#L1248-L1424) snapshots it and renders it. An already scheduled render can therefore take the first changed-opacity update before the second setter publishes its update; the owner callback is not a renderer transaction.
4. [`ForwardingRendererObserver`](https://github.com/maplibre/maplibre-native-ffi/blob/c29b61a0c45a0471d1b1d2c0bce23a458b6a6440/src/map/map.cpp#L1801-L1856) posts render callbacks through the map-owner mailbox. Compose's Android surface controller documents a separate render thread and OpenGL surface presentation. The exposed frame event contains no consumed-update or presentation ID linking it to either setter.

This is a **possible interleaving from source inspection**, not an observed intermediate frame in this session. It rules out claiming atomicity solely from the owner-thread block; it does not claim that the intermediate update was actually presented or that every two-setter sequence must fail.

The native [`RasterTileWorker::parse`](https://github.com/maplibre/maplibre-native/blob/d695deef12fc64ee075a892c2d913c45fe8c7b42/src/mln/tile/raster_tile_worker.cpp) reports a null-data tile as empty to `onParsed`, while nonempty data is decoded to a raster bucket. That source observation is not an end-to-end proof for transparent/204 imagery, current coverage, GPU readiness, or presentation.

### Partial FFI ordering path — not integrated or sufficient

1. **Documented grouping:** In FFI 0.202610.2, Kotlin `MapHandle.beginCommandGroup()`, two `setStyleLayerProperty(..., "raster-opacity", ...)` calls, and `endCommandGroup()` correspond to the [C command-group contract](https://github.com/maplibre/maplibre-native-ffi/blob/a27e607357aef2cc9c9c89d10ebba7b3bde26fe8/include/maplibre_native_c/map.h#L1188-L1242). The commands commit individually, but the map holds their render updates, including concurrent loading/camera updates, until the outermost group ends; the header says no frame shows only some grouped commands. Submit the matching end on every path and do not wait for completions between begin, setters, and end. **This is not rollback:** a failed command leaves the group open and other commands applied; ending after a partial failure can publish partial state. A successful application protocol would need to verify each outcome, handle cancellation/partial failure, control interleaving, and maintain identity; none was tested. This is an upstream ordering guarantee, not proof that these app writes ran as one successful group.
2. **Documented rendered-update correlation:** [Command completion](https://github.com/maplibre/maplibre-native-ffi/blob/a27e607357aef2cc9c9c89d10ebba7b3bde26fe8/include/maplibre_native_c/completion.h#L41-L66) reports `render_update_generation`; inside a group it denotes the update published by the outermost end. [`RenderFrameResult`](https://github.com/maplibre/maplibre-native-ffi/blob/a27e607357aef2cc9c9c89d10ebba7b3bde26fe8/include/maplibre_native_c/render_session.h#L103-L132) reports `disposition`, demand `token`, `map_update_generation`, session-target `generation`, and `frame_generation`. A host with the correct session can use [`requestFrame()` and `drainFrameResults()`](https://github.com/maplibre/maplibre-native-ffi/blob/a27e607357aef2cc9c9c89d10ebba7b3bde26fe8/bindings/kotlin/src/commonMain/kotlin/org/maplibre/nativeffi/generated/GeneratedRenderSessionOperations.kt). An actual `RENDERED` result at or after the completion's update generation identifies a render from map state including the command. The host must separately guard source/frame/viewport/style/surface identity and rule out later superseding mutations; a greater generation alone does not prove the desired opacity/source state still holds. Results can be stale or out of order and must be matched to the correct live session and demand.
3. **Rendering is not presentation or raster readiness:** The same [render-result header](https://github.com/maplibre/maplibre-native-ffi/blob/a27e607357aef2cc9c9c89d10ebba7b3bde26fe8/include/maplibre_native_c/render_session.h#L24-L33) explicitly says `RENDERED` says nothing about GPU completion. A present flag requests presentation on a supporting target, but the result is not, by itself, a physical-display/present-fence acknowledgment. Nor does drawing an update certify that every required raster tile, including empty tiles, was drawable. `acquireFrame()`, acquired-frame producer sync, and `readTexture()` concern the host's suitable texture target and require access to the correct live session; they do not automatically assert the actual composed display.
4. **No live Compose access established:** Compose 0.17.0–0.20.0 select map frame-finished events but not `MAP_TILE_ACTION`, and their event conversion does not forward tile actions. In 0.20.0 [`withPlatformMap`](https://github.com/maplibre/maplibre-compose/blob/004a0f3bea0be4a0c0705caa49f03ff0ec0273e9/lib/maplibre-compose/src/maplibreNativeMain/kotlin/org/maplibre/compose/map/PlatformMapAccess.kt) exposes a borrowed old-FFI map, whereas [`NativePresentation`](https://github.com/maplibre/maplibre-compose/blob/004a0f3bea0be4a0c0705caa49f03ff0ec0273e9/lib/maplibre-compose/src/maplibreNativeMain/kotlin/org/maplibre/compose/map/NativePresentation.kt#L53-L73) and its renderer attachment/handle are internal/private. Its [frame event conversion](https://github.com/maplibre/maplibre-compose/blob/004a0f3bea0be4a0c0705caa49f03ff0ec0273e9/lib/maplibre-compose/src/maplibreNativeMain/kotlin/org/maplibre/compose/map/MlnFfiMapEvents.kt) forwards frame stats, not the consumed native update. A separate snapshot/session is not evidence about the app's live surface. Even the newer [FFI event envelope](https://github.com/maplibre/maplibre-native-ffi/blob/6c065d9613438bea56ad67d706c4893df14a2b32/include/maplibre_native_c/runtime.h#L577-L603) says most map events carry the last published map snapshot generation, not necessarily the update consumed by a render.
5. **Tile observations are not a coverage certificate:** Newer FFI [`MAP_TILE_ACTION`](https://github.com/maplibre/maplibre-native-ffi/blob/6c065d9613438bea56ad67d706c4893df14a2b32/include/maplibre_native_c/runtime.h#L447-L464) exposes a source ID, overscaled/canonical tile identity, and operation; it does not document current viewport completeness, source-instance reuse, GPU drawable status, or the swap's presented output. No public source-specific query or documented event sequence satisfying all these requirements was identified. Inferring readiness from parse, resource delivery, source existence, Full/Idle, delays, or an app event counter remains unsound, particularly on cache hits and recreation.

As a cross-check of another public native API, Android SDK [`13.7.1`](https://github.com/maplibre/maplibre-native/releases/tag/android-v13.7.1), commit `4cf121e515d8d065b57cd555a0b231ea27ff0e5d`, exposes [`OnTileActionListener`, `OnSourceChangedListener`, and frame listeners](https://github.com/maplibre/maplibre-native/blob/4cf121e515d8d065b57cd555a0b231ea27ff0e5d/platform/android/MapLibreAndroid/src/main/java/org/maplibre/android/maps/MapView.java), and advertises rendered-feature introspection. These are a separate MapView API, not the live Compose FFI session. The inspected [raster source implementation](https://github.com/maplibre/maplibre-native/blob/4cf121e515d8d065b57cd555a0b231ea27ff0e5d/src/mln/renderer/sources/render_raster_source.cpp#L45-L57) returns empty raster `queryRenderedFeatures` and `querySourceFeatures` results; the inspected raster layer did not establish a rendered-feature-based drawable certificate. No replacement of Compose by this SDK was proposed or tested.

### Capture candidates — no completeness proof yet

| Method | What is documented; why it is not a gate pass |
| --- | --- |
| `PixelCopy` / sampled screenshots | [PixelCopy](https://developer.android.com/reference/android/view/PixelCopy) copies the most recently queued buffer on request. Intervening one-refresh frames can be missed; a window/surface copy is not automatically the complete physical display. |
| MediaProjection + `ImageReader` or `screenrecord` | [MediaProjection](https://developer.android.com/media/grow/media-projection) projects to a virtual display. [`ImageReader`](https://developer.android.com/reference/android/media/ImageReader) documents that `acquireLatestImage` drops older images, while a slow consumer can stall or drop images even when using a queue. [AOSP's screenrecord description](https://source.android.com/docs/core/graphics/layers-displays) uses a mirrored virtual display and video encoder. Requesting a refresh rate, a nominal 60 fps, or a successful recording does not independently prove every physical present was captured or account for all losses. |
| Perfetto display video + SurfaceFlinger virtual-display trace + FrameTimeline | The [immutable upstream documentation at Perfetto commit `397f1dbcd8b8a154019bea7f8ecd0f0bb7d2b044`](https://github.com/google/perfetto/blob/397f1dbcd8b8a154019bea7f8ecd0f0bb7d2b044/docs/data-sources/video-frames.md) describes `android.display.video`, `android.surfaceflinger.virtualdisplay`, and `android.surfaceflinger.frametimeline`. The second emits a packet for each composite queued to the virtual display when its device flag is enabled; trace processor joins video PTS to vsync and reports `android_video_vsync_composite_unmatched` and `android_video_vsync_present_time_ambiguous`. Video is encoded, can perturb timing, has stream/processor size limits, and capture sequence numbers are not vsync IDs. This is a promising **calibration candidate**, not proof: zero join errors only covers observed virtual-display packets, not independently missing physical presentations, trace loss, physical/virtual equivalence, or pixel fidelity. The required sources/flag and tool version have not been checked on the prior API-35 AVD. Perfetto's [FrameTimeline documentation](https://perfetto.dev/docs/data-sources/frametimeline) reports timing/jank, not pixels, and notes its SurfaceView limitation. |
| `SurfaceControl.Transaction` | Android documents [atomic SurfaceControl changes and a presentation-completed listener](https://developer.android.com/reference/android/view/SurfaceControl.Transaction) (the latter added in API 35). These operate on the caller's SurfaceControl transaction, not the two raster-layer properties inside the current Compose-owned MapLibre surface, and do not supply every displayed pixel. They do not solve this gate without a separate, unapproved compositor design. |

A possible future **test-only** capture calibration would first confirm data-source/flag availability on an appropriate device, then use an independent trusted present reference to account for every physical display refresh or demonstrate an equivalent complete live-output assertion. It must reject missing, ambiguous, truncated, or lossy/unclassifiable observations; establish physical/virtual correspondence, timestamps, identity, and full viewport/tile-edge pixel fidelity; and use deliberately injected, independently verified one-refresh basemap-only and double-opacity negative controls at varying offsets. Merely observing those controls sometimes or obtaining zero Perfetto join errors is insufficient. No such facility, device, reference, controls, or capture was built or validated here.

### Recommendation and approval boundary

Recommend **no production implementation or dependency upgrade** based on this audit. For a possible later API path, an approved scope would need a compatible Compose and Android OpenGL runtime using FFI 0.202610.2 or later, migration to its changed asynchronous API, public live-session/result access, and a separately established source/viewport/lifetime-correlated raster-drawable operation. It would also need guarded grouped handoff, committed/failed-command recovery, matched rendered and presentation evidence, and the complete-output proof above. No identified released Compose version supplies all of this; an upstream API addition or maintained fork may be necessary, and neither is authorized. SDK floors alone do not make that migration safe.

Request explicit approval before either (a) implementing a **test-only** capture/calibration prototype, with a suitable device and independent present reference, or (b) investigating/designing a narrowly scoped upstream/native/Compose API extension or fork for the missing readiness and live-result contracts. These are separate choices; capture calibration alone will not unblock readiness, and any eventual dependency/fork/production implementation needs its own approval. No task scope or gate requirement is reduced.
