## Context

`WeatherScreen` currently embeds `WeatherHero`, forecast-mode selection, the map and its route button; its map is conditional on a forecast and location. `HluNavHost` owns separate weather and route destinations, while `WeatherMap` is also reused by location and route endpoint pickers. Settings use DataStore. The requested image is a visual reference for overlay density and controls, not a requirement to replace the existing OpenFreeMap style with satellite imagery. See proposal for motivation.

## Goals / Non-Goals

**Goals:** Keep radar independent of forecast providers and scoped to the main map; use lifecycle-aware playback and a small shared main-screen shell while retaining existing ViewModels and navigation behavior.

**Non-Goals:** A server, another radar provider, a second route planner, redesign of weather cards, or radar overlays in picker maps.

## Decisions

1. **Validate the provider contract before wiring it.** Check current LibreWXR public documentation, actual metadata, permitted use, tile options, caching and attribution; record findings in the implementation summary. Fetch `https://api.librewxr.net/public/weather-maps.json` directly with the established HTTP stack, parse the returned host and observed/forecast paths and timestamps, and construct URLs only from documented options. Do not assume RainViewer compatibility guarantees a particular option or forecast availability. If access or terms cannot be verified, record the blocker rather than inventing attribution or an endpoint. Alternative: hardcode assumed tile templates; rejected as fragile and potentially noncompliant.

   **Provider evidence checked 2026-11-01:** LibreWXR's [web integration guide](https://github.com/JoshuaKimsey/LibreWXR/blob/main/docs/web-integration-guide.md), [Rain Viewer migration guide](https://github.com/JoshuaKimsey/LibreWXR/blob/main/docs/rainviewer-migration-guide.md), [public API terms](https://librewxr.net/terms.html), [upstream data-source list](https://github.com/JoshuaKimsey/LibreWXR#data-sources), and [coverage documentation](https://github.com/JoshuaKimsey/LibreWXR/blob/main/docs/coverage.md) document the contract. `GET https://api.librewxr.net/public/weather-maps.json` returned HTTP 200 at 2026-11-01 20:05 UTC (`version: "2.0"`, `host: "https://api.librewxr.net"`). Its actual shape was `radar.past` (12 `{time,path}` frames), `radar.nowcast` (6), `radar.colorSchemes` (15), and `satellite.infrared` (12); paths were `/v2/radar/<time>`. This matched the guide's documented schema; future frames are in `nowcast`, not a `forecast` field. The observations spanned 1793556600–1793563200 and nowcast 1793563800–1793566800 (Unix seconds, 10-minute intervals).

   Documented radar tile format is `{host}{path}/{size}/{z}/{x}/{y}/{color}/{smooth}_{snow}.{ext}`. Options documented by LibreWXR (not inferred from RainViewer compatibility) are size 256/512; zoom 0–12 (server-configurable); color 0–14 or 255; smoothing and snow flags 0/1; PNG or WebP; optional `arrows=light|dark`, `cells=light|dark`, and `lightning` values empty/1/true/dots/bolts. A GET using the actual latest metadata path, `https://api.librewxr.net/v2/radar/1793563200/256/7/71/44/2/1_1.png`, returned HTTP 200 `image/png` (55,509 bytes, `X-Frame-Timestamp: 1793563200`). A latest-frame tile returned `Cache-Control: public, max-age=300`; an older metadata frame returned `public, max-age=7200`. The migration guide documents these respective 5-minute and 2-hour cache lifetimes; the terms encourage caching/CDNs.

   The public-instance terms allow apps, sites, prototypes, and commercial use, with reasonable request rates; ordinary interactive animation is expressly acceptable. They prohibit bulk archive scraping, excessive sustained traffic, circumventing limits, and reselling/re-exposing the hosted endpoint as another API/proxy; service is best-effort without uptime guarantee. Terms give the LibreWXR credit example “Weather data via LibreWXR (librewxr.net)” and require applicable upstream credits without implying endorsement. The source list documents upstream licenses/credits, including the DPC Italy CC-BY-SA 4.0 exception and required “Radar-DPC” credit, plus the requested NOAA credit “Precipitation data from NOAA Enterprise Rain Rate (RRQPE).” Metadata does not identify upstream sources or attribution per tile/pixel, so no more specific per-frame credit can be inferred from it.

   A separate `/sample` URL is not part of the documented API and returned HTTP 404 (`{"detail":"Not Found"}`); it is not needed for integration. The web guide includes a documented example response, and the canonical live metadata response and an actual constructed radar tile were both verified successfully. Use the documented schema and frames from the live endpoint, not the 404 response.
2. **Own radar independently of forecast data.** A small repository exposes cached metadata and refresh/error state with bounded retry and cancellation; a lifecycle-aware state holder manages selected frames and playback. Default to latest observation when metadata first arrives, reconcile selection safely on refresh, and never misclassify future frames. Reuse HTTP and map tile caching where supported; prefetch only if the installed MapLibre APIs permit bounded, useful caching. Alternative: reuse forecast ViewModel/network model; rejected due to coupling unrelated providers.
3. **Attach an optional radar raster layer to the existing map.** Extend the main-map integration without enabling radar on other `WeatherMap` callers. Use the installed MapLibre Compose raster source/layer APIs and style lifecycle, stable identifiers, and an efficient supported source update strategy; if URL changes require layer/source replacement, do so without rebuilding the map or duplicating layers. Put raster below labels where practical and markers/controls. Preserve the existing basemap, map camera, locations, and attribution. Keep the map responsive if tiles fail. Alternative: a WebView or independent map; rejected due to duplication and lost behavior.
4. **Separate transient UI state from preferences.** Persist visibility in existing DataStore settings (default enabled); use 75% initial opacity and expose a slider. Keep selected frame/playback screen-scoped and cancel animation and requests when Map is not visible; derive labels from timestamps and device timezone. Use compact accessible Material 3 controls placed inside safe map bounds. The first phase retains the existing route button under the timeline.
5. **After radar verification, lift the primary shell above weather and route.** Coordinate `HluNavHost`, existing `ForecastMode` selection and `WeatherHero` so the compact title/settings header and Material 3 bottom bar are shared by weather modes and the existing route screen. Preserve the existing ViewModel ownership and save/restore state where practical; ensure navigation is single-top and secondary screens have sensible back behavior. Remove redundant shortcuts only in this second phase. Avoid adding a parallel navigation framework or route implementation.

## Risks / Trade-offs

- [Public service changes, coverage gaps, unclear licensing] → Verify current documentation/terms and real responses; degrade gracefully and record limitations rather than fabricate coverage or credits.
- [Rapid playback or style reload races] → Scope jobs to visibility, bound caching/retry, use stable layer identities and test reloads and rapid frame changes.
- [Existing screen assumes forecast and location] → Preserve existing empty/error and location flows while ensuring radar failure never blocks the map; test loading and unavailable states.
- [Navigation reshaping can lose state or duplicate insets] → Reuse owners, save state where practical, handle system insets once and test route/settings/back transitions on small devices.

## Migration Plan

Implement and verify radar under the current top navigation first, including the route shortcut. Then implement and verify the new shared navigation shell and remove the shortcut. DataStore defaults enable radar for existing and new installations without altering unrelated preferences. Rollback is a code rollback; radar preference keys can remain unused safely.
